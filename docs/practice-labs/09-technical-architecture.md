# 09. Practice Labs technical architecture

**Starting point:** the platform built at `9b6e7e9` (`docs/practice-labs-platform.md`, section 2), on Eleventy 3, Nunjucks, vanilla ES modules and the ecosystem workspace. This document extends it. No framework and no build-time bundler are added.

## 1. Module layout (target)

```
assets/js/practice-labs/
  registry/
    departments.js          D1–D8: id, slug, title, summary, audience, path ids (home), cross-listed ids, order
    paths.js                path index: id, slug, department, status (planned|building|complete), title, tagline, runtime ids
  paths/<path-id>/
    curriculum.js           levels → modules → lessons/projects/interview (ids, slugs, titles, layout)
    lessons/<module-id>.js  lesson content as BLOCKS (section 2), one file per module (keeps files small)
    exercises.js            checked tasks (or a re-export of an existing lab's set)
    datasets.js             data the engines load (setup SQL, JSON fixtures, files)
  engines/
    engine.js               the shared interface (section 4)
    sql/  js/  python/  java/  quiz/  rubric/  locator/  git/  ci/  shell/  http/
  components/              render functions (pure strings, build-time) + init functions (browser)
    lesson-html.js  practice-html.js  quiz-html.js  rubric-html.js  visual-html.js  cards-html.js
  learn-html.js            page assembly (exists; becomes the generic assembler)
  search-index.js          build-time JSON index for Practice Labs search
  shoplite/                E5 practice app (its own entry, HTML pages generated by its own template)
  api-sandbox/sw.js        E6 Service Worker mock API
src/_data/learn.js         (exists) → all learning pages
src/learn-pages.njk        (exists)
```

**The existing labs stay where they are** (`assets/js/tools/<lab>/`). The path folders import from them, as the SQL path already does, so no content is duplicated.

## 2. Lesson content model: blocks

The 18 SQL lessons use a fixed shape (intro, points, examples, mistakes, practise, plus extras). New paths need more variety, so lessons become an ordered list of **typed blocks**. The SQL lessons keep working through an adapter that turns the old shape into blocks.

```js
{
  id, slug, title, minutes, objectives: [], prerequisite?,
  layout: "column" | "panel",
  blocks: [
    { type: "text", heading?, paragraphs: [] },
    { type: "list", heading?, items: [] , ordered? },
    { type: "why", text }, { type: "analogy", text },
    { type: "callout", kind: "note|tip|warning|local|simulated|desktop-only", text },
    { type: "code", language, source, caption?, run?: { engine, setup? } , expected?: { kind: "table|text", value } },
    { type: "diagram", svgId, alt, description },          // SVG file in assets/img/practice-labs/, text equivalent required
    { type: "visual", visualizer, config, description },
    { type: "practice", exercises: [ids] },
    { type: "quiz", questions: [ { kind, prompt, options?, answer, explanation } ] },
    { type: "mistakes", items: [] }, { type: "realWorld", text },
    { type: "check", items: [ { q, a } ] }, { type: "summary", text }
  ],
  sources: [ "S-id or URL of official documentation consulted" ],
  reviewed: { date, by: "author", method: "how examples were verified" },
  versions?: { "playwright": "1.x" }
}
```

**Validation:** `learning/content-schema.js` gains `validateLesson`. A unit test runs it over every path, and the build fails on an invalid lesson, so no broken page can ship.

## 4. Engine interface (E1, E2 and the simulators)

```js
// engines/engine.js
export const engine = {
  id: "sql",
  label: "SQLite (in your browser)",
  size: "0.7 MB",
  load(): Promise<void>,                  // lazy, idempotent; rejects with { unavailable: true }
  run(source, ctx): Promise<RunResult>,  // { ok, output: { kind, value }, error?: { message, line? }, timedOut? }
  check(exercise, source): Promise<Verdict>  // { verdict: "correct"|"not-yet"|"cannot-check", summary, findings[], lines[] }
};
```

- **Isolation:** every engine runs in a **Web Worker**. The page enforces a time limit by terminating the worker; 3 s by default, 10 s for Python's first run, which is stated on the page.
- **Fresh state:** each run starts from fixed state. SQL already builds a fresh database for every run.
- **Built example:** the SQL runner, worker and evaluator (`tools/sql-practice-lab/`) are the reference implementation. The others copy their shape.
- **JS engine:** a dedicated Worker that runs the learner's code (as a Blob module), isolated by the Worker boundary. Content Security Policy compatibility is to be checked at build time. There is no DOM; `console` is captured; `fetch` and `importScripts` are disabled. The DOM lessons (D4) instead use a sandboxed `<iframe sandbox="allow-scripts">` with a `srcdoc` document, messages through `postMessage`, and no same-origin access.

## 5. Checkers (shared)

| Code | Implementation |
|---|---|
| RS | Existing `compareResults` |
| stdout / value | Normalised compare (trim, line endings, number tolerance) |
| tests | A tiny assertion library in the worker (`expect(x).toBe(y)`), so learners see their code's test results |
| static | Regular-expression or AST rules (for TS/JS, a small tokenizer; no TypeScript compiler) for Playwright code: e.g. "uses getByRole", "no waitForTimeout", "awaits every action" |
| plan | Run `EXPLAIN QUERY PLAN` and match a required pattern (SEARCH, index name) |
| rubric | Rule lists per artefact ([07](07-interactive-tools-catalogue.md), E4) |
| BH | A seeded-bug matcher: feature id, then field, then a behaviour keyword set |
| HT | Request and response assertions |
| LO | The count and identity of matched elements |
| GS | Goal graph equality (commit topology, ref positions, file contents) |

**Rule for every checker:** a "not yet" message describes the difference but never prints the expected answer.

## 6. Build integration

- `src/_data/learn.js` produces every page type (department, path, level, module, lesson, project, interview) from the registries.
- Pagination (built) and the sitemap collection both use the existing `sitemapOrder` pattern.
- **Build-only modules** (registries, `*-html.js`, `lessons/*.js` content) are listed in `BUILD_ONLY` through a glob helper, so lesson text is not shipped twice. The page HTML already contains the text; the browser loads only the engines and exercise data it needs.
- **Exercise data for checking** ships as a per-path JSON module, loaded only on pages with practice.
- **Search index:** a build-time `search-index.json` for Practice Labs (titles, slugs, keywords, department), under 100 KB.

### 7.1 Vendoring rule

A runtime is vendored under `assets/js/vendor/<name>/`, with:

- its LICENSE file;
- a `VERSION` note: version, source URL, SHA-256 and the date checked.

It is served same-origin with no CDN at run time. This follows the sql.js precedent and rulebook 8.8 (no third-party requests carrying user input).

## 8. Progress (rule 7.7)

- **Default (no exception approved):** no storage. Only position text ("Lesson 5 of 18") and the learner's own exports (writing-lab Markdown, project bundle) are offered.
- **Proposed exception (decision D1):** opt-in, device-only progress, the same pattern as `learning/progress-store.js`:
  - off until the learner turns it on;
  - one key, `tz-path-progress-v1`;
  - stores only lesson ids completed, as calendar dates, and the last lesson per path;
  - validated on read, at most 50 KB, with export, import and a "forget" button;
  - nothing sent anywhere.
- **Enables:** completion ticks in the roadmap, "Resume where you left off" on the path page, and module completion. **Never:** streaks, points or leaderboards.

## 9. Error handling

| Situation | Behaviour |
|---|---|
| Engine fails to load | "This browser could not start X", with the reason class (WASM, Worker, memory) and a link to the static solution |
| Time limit hit | Named cause ("stopped after 3 s"), with the usual reasons |
| Exercise data missing | The block renders a visible "This exercise is unavailable" (never a blank) and logs a console error; the build test should make this impossible |
| Service Worker unavailable | In-page shim (E6) |

## 10. Accessibility and responsiveness hooks

The architecture requires:

- every visual has `description`;
- every exercise has a label;
- every runtime action is a `<button>`;
- feedback regions are `role="status"`.

These are validated by `validateLesson` (missing `alt` or `description` fails the build).

## 11. Feature-specific sanity checks (for the development stage)

| Feature | Check |
|---|---|
| New lesson | Schema validation; the page builds; one H1; examples' expected results match a run (script); no overflow at 390 px |
| New engine | Run, check, time limit and unavailable paths on desktop and a 390 px phone emulation |
| New simulator | Goal reachable; the reference solution passes; one wrong attempt gives specific feedback |
| ShopLite release | Each seeded bug reproducible by its recorded steps; `stable` has none of them |

No full suites ([13](13-acceptance-criteria.md), section 3).
