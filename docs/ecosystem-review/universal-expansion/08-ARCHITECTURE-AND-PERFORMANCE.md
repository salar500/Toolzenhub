# 08. Architecture recommendations and performance findings

Principle: smallest change that fits the existing architecture; no new framework, backend, paid API or database; every catalog fact stored once (rule 9.2). Nothing here is approved.

## 1. Registries and taxonomy (verified current design)

Section, category, subcategory and tool are resolved from `assets/js/data/categories.js` and `tools.js`; routes, sitemap, listings and search derive from them (`taxonomy.js`, `relationships.js`, `search-index.js`, `tool-capabilities.js`). Articles use the **calculator** categories (`articleCategories` map to `categories`), so an article cannot belong to Time, Developer, Image or PDF Tools today. Learning content lives in `assets/js/learning/` (`content-schema`, `lab-shell`, `lab-page`, `scheduler`, `session`, `progress-store`, `dom`).

Recommendations:

| Area | Recommendation | Change size |
|---|---|---|
| Category taxonomy | No new section for now. If guides for non-calculator tools are approved (N18), add an **article topic** field that may name a section as well as a calculator category (O-7), or place those guides under a single "Guides" label without new categories. Prefer the first if more than six guides exist | small data change, owner decision |
| Tool registry | Unchanged. New tools register the existing way (Tool Pack spec first) | none |

## 2. Internal linking rule (B24)

Today: related lists are same-section (rule 4.2); links inside page text are allowed across sections. Proposed contextual pairs (tool to its lab, lab to its tool, calculator to its guide) are legal as **text links in the page body** and need no rule change. A rendered "Practise this" block that crosses sections needs O-4.

## 3. Learning platform foundation

Reuse the existing engine. Add only what a second subject needs: a subject pack manifest (id, title, level, prerequisites, item ids), a path definition (ordered pack ids), and a progress adapter that stays a no-op unless the visitor opts in (rule 7.7 exception limited to Smart Flashcards today). Never claim a path is complete when it has a few exercises.

## 4. What stays out

A backend, accounts, synchronisation, server-side checking, analytics events from tools, a CMS, a chart library, a UI framework, certificates.

## 5. Performance findings (B16)

**Method:** HTTP timing with `curl` against the live preview, three requests per page, plus static analysis of the built `dist-ghpages` pages: stylesheet count and size, and the ES module graph size and import depth. **No browser, Lighthouse or trace was run** (about 436 MB free RAM). The measurements come from this laptop's network path to GitHub Pages, one location.

| Measure | Result | Class |
|---|---|---|
| HTML size (gzip) | 2.4 KB (home) to 7.7 KB (All Tools); 4.7 to 6.6 KB for sample tool pages | verified |
| Time to first byte, repeat requests | 80 to 120 ms | verified |
| Time to first byte, first request of a page | 300 to 600 ms; one outlier 1.13 s in 18 requests | verified |
| Hosting | HTTP via GitHub's CDN (Varnish), `Cache-Control: max-age=600` on pages and on JS; gzip on; the 600 s value cannot be changed on GitHub Pages (secondary sources only) | verified header, P for the "cannot change" claim |
| Stylesheets per page | 15 (All Tools) to 23 (Home); 22 on a calculator, PDF tool and flashcards page; 108 to 119 KB raw, 19 to 26 KB gzip; all render-blocking `<link>` | verified (built HTML) |
| JS modules per page | 6 (All Tools) to 33 (Home); 16 to 18 on tool pages; 40 to 310 KB raw, 10 to 65 KB gzip | verified (static import graph) |
| Import depth | 4 (calculator, flashcards, All Tools), 6 (Merge PDF), 7 (Home): each level is a sequential request round trip before the next modules are known | verified (static), effect I |
| Cold versus warm navigation in a browser | not measured | NOT RUN |
| Long tasks, layout shift, image decode on the pages the owner finds slow | not measured here. The UI/UX ledger recorded a Categories CLS of about 0.075 earlier | earlier evidence |

**Reading of the evidence (inference, not proof):** the payload is small; the cost is more likely the number of requests and the depth of the module chain, on a network with high round-trip time, with only ten minutes of caching. The owner's "slow on the preview" is therefore plausibly a **request-count and round-trip** problem on this host, not a computation problem. It may not exist on Hostinger, which was not measured and must not be touched. Measured here: nothing about production.

**Not defects to fix:** the 600 s cache (hosting), first-request latency to a CDN edge (network).

**Possible, low-risk steps, only after a browser trace confirms the cause (U11):** emit one combined, minified stylesheet per page type in the preview and production builds (removing 15 to 22 requests); add `modulepreload` hints for the known import chain of each page type; keep dynamic loading of tool modules. Each is a build-time change that must keep all URLs and test through the build, and should be measured before and after on one page type. This is shared-architecture work with many consumers, so by rule 10.11 it is verified when it is made, and it should not be started on the strength of this analysis alone.

**Measure properly (Phase 2, first):** one throttled mobile trace and one desktop trace for Home, All Tools, one calculator, one PDF tool and one lab; cold and warm; report long tasks, request waterfall and CLS. Run it where memory allows (rule 10.3 prefers a temporary read-only runner when local RAM is too low, which needs a branch and the owner's push approval, so ask first).
